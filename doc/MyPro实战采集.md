## 怎么记录一场真实战斗

11 月 24 日 19 时，本项目 PID 35412 的同尺寸实战已去掉命令行帧率。战外稳定段的游戏请求值仍为 50。两场长战低点之后的最高十秒为 29.60／29.75 呈现 FPS，原版 PID 142192 的归档为 49.4／45.7 原生 FPS。当前包可从慢回调找到 9 个具体换宠区间；MyPro 的这份采集使用不同口径，缺少逐次换宠的同类标记。[本轮逐次换宠](goto与子树遍历.md#19-时实战的九次换亚比)

双击 [MyPro 战斗采集入口](../dist/mypro-battle-monitor-20261124/run-mypro-monitor.cmd)，它会启动根目录的 `MyPro v1.0.1.exe`。首次在这个独立配置中手动登录，以后沿用包内的登录资料和资源缓存。入口使用 DX 后端和 960×560，保留原版快速跳帧和内置战斗资源。MyPro 采集脚本已去掉 `--frame-rate 50`，新会话在 `session.json` 中以 `targetFps: null` 表示未传入帧率参数。本项目在 PID 35412 实战之后按用户要求把战斗测试包设为全场景强制 60 FPS；两者的目标设置应单独记录。上表的 PID 142192 和 59684 均为改动前的实测。复测时保持相同窗口、阵容、出招顺序和特效设置，并注明是否首次加载。

打完几场后，等回到场景再正常关闭 **MyPro 游戏窗口**，保留采集窗口直到它输出本次报告目录。每次运行单独保存在 `dist/mypro-battle-monitor-20261124/runs/<日期时间-编号>/`。

| 文件 | 用途 |
| --- | --- |
| `session.json` | 确认 PID、测试设置、开始和结束时间以及退出码。 |
| `telemetry.log` | 按原始 UTC 时间查看战斗进退场、约每秒的 GC 维护、显示对象快照和按类新建数。 |
| `mem.csv` | 查看整个进程的帧率、渲染耗时、存活 GC 节点和完整收集计数。CSV 约每秒一行，本地影片中帧率和渲染统计约十秒刷新一次。 |
| `summary.json` | `telemetry.battles` 每场列出 GC 轮数、毫秒数、存活节点数的可见降幅，以及已报告的各类新建实例数。只汇总两端都在本场的区间。跨进退场的堆快照保存在 `heapSnapshots`，缺少可归属区间时显示 `null`。 |

已用本地影片和 MyPro 的模拟进退场验收入口。PID 83028 的 21 行 CSV 和 39 条性能事件均已核对，性能事件逐行匹配原始日志。该次三次堆普查的 `census_ms` 依次为 2、1、1 ms，线上大堆的普查开销需读实战日志。[启动器](../src/tools/measure-mypro-battle.py) · [汇总规则](../src/tools/summarize-mypro-battle.py) · [本次验收](../build/mypro-battle-monitor-20261124/offline-monitor/runs/20261124-142231-55a2a3ae/summary.json)

## 测得到什么

项目根目录的 `MyPro v1.0.1.exe` 已提供 `--mem-log` 和堆普查开关 `AOQI_HEAP_CENSUS`。前者约每秒写一行 CSV，后者开启按类创建计数。测试直接运行该发行程序，保留其内置战斗 SWF 和原生优化。

| 观测值 | 可以回答的问题 | 读数条件 |
| --- | --- | --- |
| `fps`、`render_ms` | MyPro 在采样时报告的帧率和渲染耗时 | 两列沿用 MyPro 的统计口径。与 v2 对照时固定分辨率、帧率上限、技能和特效设置。 |
| `live_gc_objects`、`full_collections`、`last_pause_ms` | 采样时 GC 节点有多少、完整收集计数如何变化、最近一次停顿持续多久 | 两次存量之差同时受到新分配和释放影响。`last_pause_ms` 是最近一次的值，跨行求和会重复计算。 |
| `MOVIE_RECLAIM_SEC` | 该报告区间的维护轮数、GC 耗时，以及标记和清扫耗时 | `rounds` 和 CSV 的 `full_collections` 分开统计。电影维护记录里的 `freed` 也不能当作整个 GC 堆销毁的节点数。 |
| `MOVIE_RECLAIM` | 每次电影库维护中降级、重新启用及释放的登记项，以及标记和清扫耗时 | 每场在 `movieReclaim` 中单独汇总。这次实战同时见到逐次报告释放非零、对应秒报释放为零。 |
| `HEAP_CREATED` | 两次报告间，MyPro 按显示对象类列出了多少新建实例 | 在同时创建 28 个不同子类的实验中只报了数量最高的 14 类。未列出的类也可能有新建，跨进退场的报告不计入单场合计。 |
| `HEAP_STAGE`、`HEAP_CENSUS`、`BATTLE_MEM`、`BATTLE_FOLLOWUP_MEM` | 查看显示对象快照、堆普查及结算前后的资源读数 | `orphans` 是快照中的无父对象数。一次嵌套跳帧可以反复遍历已有对象，期间可能没有新建任何实例。 |
| `BATTLE_SCOPE_RECLAIM` | 若 MyPro 发出此记录，可查看本场被标记集合的 `tagged`、`freed_after_cycle` 和耗时 | 文件中能定位该事件及其字段。模拟进退场时没有收到此事件，汇总仅在收到时保留原值。 |

离线影片分 8 轮各创建 128 个 `Bitmap` 和 1 个 `Sprite`。原版 MyPro 的两次创建报告合起来恰好是 **1,024 个 Bitmap、8 个 Sprite**。同次测试有 20 行 CSV，维护报告的 `rounds` 合计 15，CSV 的 `full_collections` 从 0 增为 1。一次采样间节点净减 30,274，同次维护秒报的 `freed` 全部为零。此例可用于核对两个计数的口径。[夹具源码](../build/mypro-runtime-20261124/Rounds.as) · [原版 CSV](../build/mypro-battle-monitor-20261124/gc/original-qv2aajmz/mem.csv) · [原版诊断日志](../build/mypro-battle-monitor-20261124/gc/original-qv2aajmz/data/MyPro.log)

每场的 `gc.sampledLiveNodeDrops` 只累加相邻原生秒报中看得见的节点下降量，`sampledLiveNodePairs` 给出可比较的对数。例如同场 120 → 100 → 110 → 90，三对中观测到的降幅合计 40。两次采样之间新建对象会抵消一部分释放，因此实际释放总量仍为未知。[离线验收汇总与原始记录索引](evidence/mypro-runtime-20261124/battle-monitor-validation.json)

28 个 `Sprite` 子类的创建数从 1 到 28，日志列出创建 28 次到 15 次的子类。汇总按原版列出的次数累加，场内某一类的合计可能低于真实创建数。[子类对照源码](../build/mypro-battle-monitor-20261124/gc/ClassProbe.as) · [原版分类输出](../build/mypro-battle-monitor-20261124/gc/original-classes-q5upk9jl/data/MyPro.log)

## 嵌套跳帧与无父对象

根据下列原版观测，当前项目已提供可与 v2 在同一 EXE 内切换的战斗局部跳帧，并提供可独立启用的发光滤镜融合。默认包 PID 59684 的两场实战已确认局部跳帧命中。[跳帧与实战入口](goto与子树遍历.md#11-月-24-日-mypro-战斗跳帧候选) · [发光滤镜验收](MyPro对照与移植.md#11-月-24-日发光滤镜融合)

在同一份本地影片的普通帧中，分别让离台和在台目标执行 37 次跨帧 `gotoAndStop`。影片直接计数目标帧脚本、全局 `FRAME_CONSTRUCTED` 与 `EXIT_FRAME` 广播，并准备了两个与跳帧目标无关、已经有待执行帧脚本的对象。四组都创建了相同的 64 个测试影片实例，跳帧期间新建该类实例数均为零。

| 程序及设置 | 每批 37 次跳帧内额外的构造完成广播／退出帧广播 | 无关无父对象和在台对象的脚本何时执行 |
| --- | ---: | --- |
| MyPro 默认、MyPro 显式 `AOQI_FAST_GOTO=1` | 0／0 | 跳帧返回时均未执行，下一次普通帧观测时均已执行一次 |
| 同一 MyPro，显式 `AOQI_FAST_GOTO=0` | 37／37 | 两个脚本都在跳帧返回前执行 |
| 本项目 v2 优化包 | 37／37 | 两个脚本都在跳帧返回前执行 |

目标本身的脚本在四组中均按测试输入运行。MyPro 默认的快速跳帧改变了其他对象收到广播和执行脚本的时机，v2 仍保留全局调度顺序。广播是脚本可观察事件，无法由这些数据换算出 MyPro 内部逐根调用 `construct_frame` 的精确次数。另在四组中各释放 32 个测试对象的外部引用，到第 20 帧，对应弱键都已消失，保留引用的 32 个对象仍可访问。[测试影片源码](../build/mypro-battle-monitor-20261124/fixture/Lifetime.as) · [四组原始观测](../build/mypro-battle-monitor-20261124/fixture/lifetime-comparison.json)

另一份影片保留 1,780 个无父根。预热后连续五批共执行 18,880 次跳帧，MyPro 开关各用四个独立进程交替运行。宿主日志计时中位数从关闭时的 **1,143.038 ms** 降至开启时的 **3.509 ms**。这组数据定位了重复跳帧开销，也观测到依赖全局广播的重挂回调发生变化。真实战斗中该路径占多少帧时间，仍需结合相同阵容和技能的实测。[负载与逐进程耗时](../build/mypro-battle-monitor-20261124/fixture/benchmark-wall.json)
