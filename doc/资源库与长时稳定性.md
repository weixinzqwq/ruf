# 资源库与长时稳定性

## 原因与实现

2026-11-05约十分钟混合战斗与录像测试中，用户约第五分钟开始感觉卡顿。回收仍正常推进，但后半程帧更新变重、电影与符号资源数量增加。

后续实现：电影拥有自己的符号库，全局索引改用弱引用；类到符号的关系随类保留；完整回收后清理失效索引并盘点资源。标记期GPU维护避免升级弱引用，防止维护过程本身保住闲置库。仍被游戏引用的类、显示对象和资源不会被强制释放。

入口：`src/optimization/engine/core/src/library.rs`、`core/src/player.rs`、`core/src/frame_profile.rs`及渲染缓存维护。帧阶段计时采用互斥口径，不能把父子包含时间相加。

## 测试结果与边界

| 原十分钟长测 | 前五分钟 | 后五分钟 |
| --- | ---: | ---: |
| 显示FPS | 25.55 | 17.42 |
| 每逻辑帧更新 | 10.59ms | 25.35ms |
| 每次绘制 | 13.75ms | 17.47ms |
| GPU工作均值 | 10.17ms | 9.68ms |

全程显示均值21.48 FPS。主要恶化在帧更新，不能简单归因为显卡算力不足。场景复杂度不同，亦不能把所有下降归因为资源积累。该采集发生在后续资源库调整之前，不能当作调整后的失败或成功证据。

资源库调整交付时的核心157项、GC33项等检查记录见[交付证据](evidence/history/frame-library-20261105/delivery.json)。**未找到随后同场景首尾长测验收，因此长期稳定性仍待验证。**

## 操作与验收

1. 在固定窗口、画质和地图下记录起始静置状态。
2. 进行10～15分钟固定轮次战斗、切换模型和地图，再返回原场景静置。
3. 比较首尾同场景FPS、长帧、帧更新阶段、完整GC周期后的对象和资源库数量及显存基线。
4. 同时验证资源再次加载、模型显示与面板复开；数量下降不能以显示丢失为代价。

库盘点是完整回收结束后的值，旧采样瞬间盘点与新值不可直接比较。原始采集为[evidence/capture](evidence/capture/)中的`pmcap-aola-native-long-test.exe-261105-175722.csv`；完整原报告为[历史说明归档](archive/历史说明与脚本.zip)中的`LONG-RUN-RESULTS.md`。
