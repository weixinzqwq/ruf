## 关闭请求之后

1. 主线程收到 `CloseRequested` 后退出事件循环。若它当时正在执行长脚本、绘制或同步缓存 I/O，消息可能先排队。[关窗分支及退出回调](../src/optimization/engine/desktop/src/app.rs)
2. 退出回调先释放登录 WebView，再写最终采样，随后同步释放主窗口及其持有的对象。Player 在析构时遍历 SharedObject。本包使用内存存储，仍有序列化开销。GC arena 析构会在同一轮中遍历其节点，调用尚存活对象的析构并释放分配。[Player 析构](../src/optimization/engine/core/src/player.rs) · [GC arena 析构](../src/optimization/engine/core/aoqi-gc-arena/src/context.rs) · [宿主配置](../src/optimization/engine/desktop/src/main.rs)
3. 释放 DX12 Surface 时会等呈现队列，释放最后一个渲染队列时还可能等 GPU fence。底层等待可使用 `INFINITE`，实际耗时取决于待完成的工作。若创建了 WASAPI 音频流，其析构还会通知并等待音频线程退出。最后 Tokio 的 `shutdown_timeout(1s)` 仅限制 Tokio 这一步。[呈现队列等待](../deps/vendor/wgpu-hal-30.0.1/src/dx12/device.rs) · [渲染队列等待](../deps/vendor/wgpu-hal-30.0.1/src/dx12/mod.rs) · [音频线程](../deps/vendor/cpal-0.16.0/src/host/wasapi/stream.rs)

对用户提供的 MyPro EXE 做了 PE 静态检查。已定位的正常关窗路径会处理 SharedObject，设置事件循环退出标志，并在返回后执行 App 析构、递减 Player 引用。在正常分支中未发现直接强杀进程的依据。对方二进制含 `TerminateProcess` 导入，异常处理和 CRT 路径确实会引用它。静态分析无法给正常关窗过程分配毫秒数。[MyPro 原件](../MyPro%20v1.0.1.exe)

| `0x140508a2a`、`0x14016f37c`、`0x140166c80` | WM_CLOSE 进入应用关闭分支 |

## 在新测试包定位最终采样后的耗时

这次用 [11 月 24 日测试包的 run-game.cmd](../dist/aola-close-phases-20261124/run-game.cmd) 启动。该入口沿用长时战斗维护设置，另开启退出计时。新包使用自己的 `aola-data`，首次启动需手动登录。打完几场战斗后保留游戏窗口，在项目根目录运行包内脚本，脚本会向该包的窗口投递一次普通关窗消息。

```powershell

```

若同一包运行了多个实例，可以先用 `-Check` 查看候选 PID，再加 `-GameProcessId <PID>` 指定本次游戏。结果保存在该包的 `aola-data/diagnostics`。读取最新的 `close-timing-*.json`，其中的 `closePhasesFile` 指向同一 PID、同次启动的逐段日志，`performance-*-<PID>.jsonl` 的末行记录战斗进出计数和最终采样时间。脚本等待上限为 15 秒，超时仍保留已写出的阶段起点。如果进程稍后自行退出，逐段日志会继续写到 `finish`。

| 要回答的问题 | 如何读数 |
| --- | --- |
| 等待发生在程序记录的退出阶段之内还是之后？ | 对比 `finalToPhaseFinishWallMs`（最终游戏采样至应用收尾末行）和 `phaseFinishToProcessExitWallMs`（末行至 Windows 进程退出）。这两项使用毫秒墙钟。 |
| Player 和 GC 各花了多久？ | 完整记录的 `phaseSummary.playerDropMs` 是主线程实际 Player 析构的包含时间，`gcDropMs` 是 GC 销毁剩余节点的包含时间。在原始 `gc-drop-all` 的起止行可看到进入时的节点数和结束时的剩余数。若只停留在登录窗口，Player 可能还未创建，对应字段为 `null`。 |
| 谁占用了主线程？ | `slowestMainThreadSelf` 按阶段名称汇总独占时间，列出最慢三项。原始日志的 `durationUs` 含同线程子阶段，`selfUs` 扣除直接子阶段。`id/parent/thread` 标明实际嵌套，父子包含时间相加会重复计算。 |
| GPU 是在释放资源还是在等待？ | 阶段结束行的 `gpuResourceDrops` 记录该线程在这段时间里完成的 DX12 缓冲、纹理、纹理视图和绑定组销毁次数及合计纳秒。看 `gc-drop-all` 等阶段即可定位释放发生的位置。`phaseSummary.gpuResourceDrops` 汇总所有线程，并换算为毫秒。它测量 CPU 执行释放调用的时间，其中可能有驱动调用；多线程累计值可能重叠。呈现栅栏、渲染栅栏的等待分别有 `dx12-present-fence-wait`、`dx12-render-fence-wait` 两个计时段。 |
| 其他时间花在哪里？ | `final-log-write` 是最终采样的 JSON 序列化、写入和刷新。`gui-drop`、`shared-object-flush`、`player-renderer-drop`、`player-audio-drop`、`tokio-shutdown`、`event-loop-tail`、`app-drop` 分别覆盖窗口组件、存储、渲染、音频及运行时收尾。 |

GPU 的逐类计数与所在阶段的包含时间重叠。判断三场战斗新增的约 8 秒时，优先对比同一测试包零战斗与多场战斗的独占耗时，再查看最慢阶段内的资源和等待明细。获得完整的正常退出记录时 `phaseSummary.completed` 为 `true`。原始记录缺少结束行时，保留其最后一个 `begin` 用于定位仍在执行的工作。[退出记录器](../src/optimization/engine/desktop/src/aola_close_phases.rs) · [包内测量脚本](../dist/aola-close-phases-20261124/measure-game-close.ps1)

阶段使用单调时钟计时。每个边界写一行，资源释放只累计次数和耗时。若后台线程的释放跨越采集起止，`workerBoundaryEvents` 会列出这类边界的数量；主线程完整时仍可读其排名。GPU 全进程汇总只统计采集期间开始且已完成计数的调用。采集本身的计时、计数和文件写入也有开销。应用末行与操作系统的实际退出由两个进程分别记录，墙钟以整毫秒表示，短区间会受 Windows 时钟分辨率影响。
