### 一轮 GC 怎样从标记走到释放

播放器从舞台、虚拟机状态、定时器等仍可访问的入口出发，沿强引用标记仍要保留的对象。例如，亚比影片已经移出舞台时，定时器回调仍可能引用它。增量标记把检查引用的工作分到多个游戏帧，每次接着上次的进度做。两次切片之间脚本仍可修改引用，写屏障会把有必要重新检查的对象加入队列。普通标记、重新标记、已满足条件的弱键字典值以及根都处理完后，收集器当步切换到清扫。清扫逐个处理节点，可以边扫边释放，扫到末尾才把完成周期数加一。若只有弱引用还在，收集器可先析构内容，保留弱引用判断对象是否存活所需的节点。[播放器的引用入口](../src/optimization/engine/core/src/player.rs) · [标记和清扫实现](../src/optimization/engine/core/aoqi-gc-arena/src/context.rs)

默认退场调用 `finish_cycle()`，主线程连续执行至当前周期结束。切片入口跳过这次主清，约 2.2 秒后在可执行 GC 的帧里调用一次预算调度。日常 GC 照常推进同一个周期。4 毫秒是每次切片的时间目标，检查发生在工作步骤之间，单个步骤可以超时。退场任务做完这次切片就结束，没有专门调度后续切片直至清扫完成。PID 3776 在首战前已经完成 8 个周期、释放 3,599,384 个节点，此后的 402.809 秒没有新周期完成，也没有节点被析构或释放。现有日志能定位到标记阶段，尚不能区分首次扫描积压、对象重新入队和弱键触发的后续扫描各占多少。[两种调度入口](../src/optimization/engine/core/src/player/aoqi_gc.rs) · [单步与完成整个周期](../src/optimization/engine/core/aoqi-gc-arena/src/arena.rs) · [同次实战计数](evidence/mypro-runtime-20261124/live-3776-sliced.json)

### 实现与记录口径

- 普通 AS3 `Dictionary(true)` 对对象键按身份弱引用。GC 追踪到存活字典和外部仍可达的键时，继续追踪关联的对象值，直到跨字典的引用链都处理完。只有字典自身还持有的键值环可以消失。字符串、数字等基本类型键和 `Dictionary(false)` 延用原有规则。FairyGUI 的显示对象所有者扩展有自己的存储路径。[字典实现](../src/optimization/engine/core/src/avm2/object/dictionary_object.rs) · [收集器](../src/optimization/engine/core/aoqi-gc-arena/src/context.rs)
- 已识别的战斗面板正常完成退场后，播放器在下一个可执行 GC 的帧边界完成当前周期，并维护电影库和声音定义。约 2.2 秒后再按当时登记电影数补清理，超过 305 部完成一个周期，最多 305 部使用预算切片。MyPro 使用两个登记表长度之和，本引擎按唯一电影登记表计数。新战斗进场会取消前一场尚未执行的维护。[战后调度](../src/optimization/engine/core/src/player/aoqi_gc.rs)
- [上一版战后策略对照](../dist/aola-weak-battle-20261124/run-previous-battle-cleanup.cmd)保留同一 EXE、弱键机制、声音和纹理策略及退出计时，仅把战后清理恢复为一次延迟切片。可用于比较结算帧停顿。

如果整场都没有 `battle-enter` 或正常退出后没有 `battle-exit`，该场的面板生命周期还没有被完整识别。若只缺补清理，先核对上次主清理完成到下一次进场或关窗之间是否留出了约 2.2 秒。

| 查看位置 | 如何判断 |
| --- | --- |
| `startup-*-PID.jsonl` 的 `battle-main-gc`、`battle-followup-gc` | 按 `battleId` 配对。看 `mode`、`cyclesCompleted` 判断完整周期或切片。看 `dropped`（已析构的节点内容）、`freed`（已释放的分配节点）、`weakEntriesPruned`（已从存活弱字典移除的死键条目）判断实际工作量。三个计数不可相加。 |

### 官方素材中的实际使用点

扫描 15 份本地 SWF 的顶层 ABC，按已解析的类名和构造参数检查。两份版本化 `petfightnew` 的直接调用中，`ServicePool._serviceMap`、`FightBitmapDataCache._cachePool` 均是无参构造，仍采用普通强键。相反，官方加载器的 `InspectorErrorWatch` 明确用 `new Dictionary(true)` 构造 `urlCacheMaps`。加载完成时 `DomainLoader.onLoadByteComplete` 调用单例的 `watch`；当 LoaderInfo 具有 `uncaughtErrorEvents` 属性时，写入 **LoaderInfo 对象键 → URL 字符串值**。这条登记独立于 debug 开关。仅按类名匹配或看到后台调试面板的字典不足以定位这个路径。[实际构造指令与扫描范围](evidence/mypro-runtime-20261124/official-dictionary-sites.json)

在两份发行程序上，主影片、刚创建的 Loader 和加载完成的子影片，其 LoaderInfo 均通过上述属性判断，也都能取得事件分发器。实验分四轮完成 96 次本地子影片加载，强键和弱键各使用 48 个不同的子 LoaderInfo，各加一个常驻对象。两组生命周期分别覆盖显式卸载，以及更接近官方 `DomainLoader.disposeLoader` 的做法。后一组 Loader 从未挂上舞台，完成后移除加载监听，放开持有引用，全程没有调用 `unload`。这组实验复现了官方代码的持有方式，字典的登记时点与完整游戏有差异。[属性与监听实测](evidence/mypro-runtime-20261124/loader-info-runs.json) · [官方 DomainLoader](../build/swf-patches/ownership-20261121/loader/scripts/mmo/loader/scheduler/DomainLoader.as)

两组实验在第 245 帧得到了相同的结果。**当前包和 MyPro 都还能枚举 49 个 LoaderInfo 弱键**，强键对照也各有 49 个。同一进程另行插入的 3,072 个普通对象弱键，在 MyPro 中全部消失，当前包仍可枚举全部 3,072 个。实测确认了普通对象弱键的回收差异。线上每场产生多少 LoaderInfo、谁还持有它们、是否仍连接大块资源，现有性能日志均未按对象记录。[显式卸载的同进程对照](evidence/mypro-runtime-20261124/loader-info-positive.json) · [按官方持有方式复测](evidence/mypro-runtime-20261124/loader-info-owner-release.json)

### 战后 GC 策略的实质差异

按原 EXE 的 PE 异常表界定函数，再对照实际 x64 指令、分支目标与常量。MyPro 宿主记录的战斗状态包含场景进入、结算和超时等分支。进入已定位的战后主维护分支时，`0x14015a44a → 0x1400b9d00 → 0x1409debc0` 会同步把 GC 的当前周期推进到完成，再做资源维护。一处宿主分支另安排约 2.2 秒后的补清理。到期后，两个 library 登记表的长度之和 **超过 305** 才再次走完整收集入口；较小规模走渐进入口，后者在指定模式下会主动提高收集债务。该阈值和债务值属于 MyPro 的内部计量。一次完成当前周期仍会保留可达对象。[原 EXE 调用点与收集循环](evidence/mypro-runtime-20261124/mypro-gc-policy.json)

本项目在已确认的战斗面板正常退场后登记 2.2 秒延迟，到期取得一个有预算的切片后即消耗请求。正在进行的收集周期仍可在后续帧继续。PID 116868 的三次补切片分别在退场后 2.229、2.226、2.442 秒执行。用相邻性能采样夹出下一次周期完成时刻，第三场在退出后 **7.534～12.553 秒**之间。终局已经完成 28 轮、累计释放 30,090,078 个节点，同时资源库累计登记 1,170 部电影、登记表累计移除 0 项。这里值得追查的是哪些强引用仍可达，以及多快能清掉已不可达对象。直接照搬同步完整 GC 也可能把退出的停顿转移到战斗结算。[当前调度](../src/optimization/engine/core/src/player/aoqi_gc.rs) · [退场事件与采样窗口](evidence/mypro-runtime-20261124/battle-windows.json)

| 报告项 | 在本项目中的处理与依据 |
| --- | --- |
| E01–E04 临时纹理 | 主渲染和离屏使用同一套池。实验组在连续 2 帧没有使用某个规格后，只保留 1 张闲置纹理；达到 31 帧再清理冷规格和空桶。借出中的纹理保留归还路径。热规格仍可复用多张纹理，显式设置的更短寿命仍生效。256 MiB 全池闲置预算在归还时执行，未引入报告中的第二个 16 MiB 池或每 16 次申请全池检查。 |
| E05–E06 声音定义 | 原混音器缺少释放已注册声音的路径。实验组让电影符号库、跨库导入和脚本 Sound 对象保有声音数据的所有权。一次渐进回收确实结束后，混音器检查持有者与播放实例，释放已无人持有的定义。播放中、等待完成通知及未移交所有权的声音继续可用。 |
| E07 小声音切片 | 现有嵌入声音注册已只复制标签内的编码数据；MP3 的两字节 seek 独立保存。对这条路径补了回归。按时间轴流式读取的声音沿用其流数据的生命周期。 |

| E09 首次进场维护 | 官方 play SWF 的 `LoadSceneCommand` 在加入房间、装载资源和初始化视图后执行 `LoadSceneSuccCommand.execute`，其中广播 `SCENE_INITED`。副本 `LoadFBCommand` 也调用这个成功回调。历史 31 次宿主会话里可见的 `setSWFIsReady` 属于加载器阶段。当前引擎在空闲且没有分配债务时，距上轮回收完成满 5 秒即可开始下一轮。没有证据把多战后衰减定位到首场景结束的 3.2 秒或 12.2 秒，因此首次场景的额外调度留作单独实验。 |
| E10 更短的网格、位图闲置阈值 | 游戏仍在引用的素材和短间隔复用都会影响重建成本。本项目在允许的 GC 阶段按帧扫描，限制 256 步、约 250 µs，网格与满足独占条件的位图使用 30 秒阈值。旧日志无法识别哪些素材在报告的亚秒阈值后马上会被重新显示，因此沿用该阈值。合作方用两个 library 登记表合计超过 305 项触发完整 GC；本项目的电影数统计口径与之不同，未移植这个阈值。 |
| E11–E13 提交、暂存与在途帧 | 本地离屏常规批次原已异步提交。实验组只合并连续的小位图上传，每批至多 8 次，每块宽高各不超过 64 像素。绘制、过滤器、着色器操作、大块写入和提交边界会打断连续性；读回仍等候相应工作。保留原离屏批次、64 KiB staging belt 和在途帧配置。 |

## 同场景复测

战中掉帧可按同一 PID 分开看。118488 第一场结束前，5.052 秒仅呈现 9 帧，401 次嵌套跳帧使无父对象构造和帧脚本各遍历 410 遍。两阶段合计 4.132 秒，同窗 GC 用了 60.9 ms。第一场退场后，无父登记槽随后由 5,106 降至 419。弱键清理、槽位减少和逐帧遍历次数各有独立计数。[无父对象的调度、可回收条件与原始性能日志](goto与子树遍历.md#战斗中无父对象为什么仍会运行)

11 月 24 日复核了用户反馈的实战关窗停顿。两次长局中的渐进 GC 均有大量实际释放，末次采样以后仍要同步析构。可用新计时脚本记录最终采样到进程结束的时段。[退出路径、离线 A/B 与操作说明](游戏关闭耗时.md)

1. 打开本包的 `run-original-maintenance.cmd`，另一次打开同目录的 `run-game.cmd`。两次使用同样的窗口尺寸、DPI、50 FPS 设置、地图、亚比、技能、操作顺序和战斗轮数。两组共用该包自己的数据目录，可先预热相同资源，再交替两组顺序。
2. 用同一地图固定视角作为重复观测点。每次退场都回到该位置并停留相近时间，记录第几战和经过的分钟数。关注 2、10、30 和 60 分钟时前两分钟的帧间隔，以及回到地图后声音和纹理能否回落。
3. 正常退出，分别取 `aola-data/diagnostics/performance-*.jsonl`。在包目录运行下方命令，按顺序给出两个文件的实际路径。脚本取最后一个 Player，检查 A/B 方向，并报告窗口、设置和各观测点。若战斗进出计数为零，先核对是否加载了可识别的战斗版本。

```powershell
python .\compare-long-run.py ".\aola-data\diagnostics\performance-对照.jsonl" ".\aola-data\diagnostics\performance-优化.jsonl"
```

`hostPresentGaps` 按成功提交宿主画面的相邻时刻分桶，P95/P99 给出所在桶的上界。窗口调整、最小化和场景切换都会影响它。`audioDefinitions` 给出当前注册项、编码字节、播放实例和累计释放数。`battleMaintenance` 给出进场、退场、已执行的延迟切片和待办状态。对应的 `startup-*.jsonl` 还会逐次记录 `battle-enter`、`battle-exit` 和 `battle-followup-gc`，可按宿主经过的毫秒与性能采样对齐。判断长测结果时，应同时查看进程私有字节、纹理池命中与新建、宿主展示间隔以及相同轮次的画面和声音。
