## 1. 目标与范围

先在给定 SWF 中明确特效和面板的生命周期，在退出时停止其拥有的活动、解除不再需要的引用，并限制空闲缓存与对象池；这些改动通过验收后，再根据剩余性能热点处理高成本特效。

首批交付以一个有确定复现步骤的面板或特效为试点，保持画面、交互、业务回调和播放时序。实际 SWF、版本、类、方法及预算数值由 P0 定位后填写，不根据文件名或现象猜测。

计划制定时只建立了任务文档。本轮进入优化源码线的实施和验收，保留帧脚本、同帧 goto 和共享资源原有语义。

## 3. 生命周期与所有权约束

### 3.1 明确停用、回池和最终销毁

| 状态／操作 | 必须完成的处理 | 验证重点 |
| --- | --- | --- |
| `ACTIVE`／启用 | 注册本对象需要的监听、计时与更新任务，恢复显示状态 | 重复启用不能重复注册；回池复用时不携带旧场景引用 |
| `INACTIVE`／停用 | 撤销本对象拥有的更新注册，停止其计时器，按业务规则取消纯显示任务 | 对象可以保留，但不能继续做不必要的工作 |
| 回池 | 先停用，清理旧面板／角色／场景引用，重置经确认可重置的状态 | `gotoAndStop(1)` 可能执行帧脚本，不能作为通用无副作用重置 |
| `DESTROYED`／最终销毁 | 注销外部注册，移出管理器，释放独占资源，解除所有权引用 | 清理必须幂等；不得再次启用已销毁对象 |
| 异步返回 | 通过当前状态或实例代次识别过期结果 | 旧加载／补间回调不能重新挂载已停用对象；共享结果按所有权处理 |

这些是补丁需要满足的行为约束，不要求为所有反编译类统一加入一套新状态机。优先复用目标类现有的启用、关闭、完成、dispose 等入口，选择改动最小且可验证的位置。

### 3.2 清理动作与业务行为同时核对

每个目标必须建立“注册位置—拥有者—结束入口—清理动作—保留行为”表，至少覆盖：

- `ENTER_FRAME`、全局事件总线、Stage 监听和游戏更新列表：使用原事件源、原函数引用及相同 `useCapture` 注销；移除后 `stage` 可能为空，应保存或找到原注册源。
- Timer、延迟任务、补间与加载回调：仅处理目标拥有的活动。`Timer.stop()` 不替代注销监听；是否 `reset()` 由复用语义决定。
- 战斗完成、技能结算、恢复输入与释放等待条件：保持原时序及业务完成通知恰好一次。允许取消的装饰性活动与必须完成的业务活动分别列明。
- `visible=false`、`stop()`、`removeChild()` 都不作为完整生命周期结束的证明；`REMOVED_FROM_STAGE` 也可能来自重挂父节点或临时回池。
- 只追踪真实可达引用链。不能断言所有自监听对象都会泄漏，也不能将 orphan 数量、访问次数或尚未完成 GC 时的分配数直接当作泄漏数量。

### 3.3 位图、缓存和池的边界

- 独占临时 `BitmapData`：最后使用结束后释放；防止重复释放和释放后继续访问。
- 共享贴图、类／符号资源：由明确的资源拥有者管理，单个面板关闭不能销毁其他消费者仍在使用的资源。
- 空闲缓存和池对象：同时设置条目数与估算字节预算，记录命中、淘汰、保留量与高水位。字节估算需注明是否只含像素，不能当作精确 GPU 驻留量。
- 正在使用的资源不参与淘汰；活跃资源超过预算时记录压力，不通过破坏使用者来满足限额。预算硬约束针对可淘汰的空闲保留部分。
- 大型一次性对象可直接销毁。对象池不是默认必选优化；只有重复创建成本得到证据支持后才引入或扩展。

| 游戏退出后是否还在工作 | 帧阶段和慢回调定位信息 | 试点拥有者的注册／注销、Timer、更新列表与异步返回计数 |
| 对象与资源是否收敛 | GC 周期、分配计数与回收后资源库盘点 | 同一场景／循环结束点的拥有者残留、独占 BitmapData 数量及估算字节 |
| 空闲保留是否受控 | 引擎纹理池统计 | SWF 缓存／池条目、估算字节、高水位、命中、淘汰及在用／空闲区分 |
| 卡顿是否减少 | 当前阶段汇总及既有 PresentMon 采集方法 | 原始逐帧时长或独立事件序列；不能用周期均值的分位冒充逐帧 p95／p99 |
| 业务是否保持正确 | 当前人工复现流程 | 完成事件、输入恢复、重复启用、取消和资源重建的针对性验证 |

尽量对选定类和操作周期计数，避免给整个 VM 增加高频详细日志。必要的新观测在原版与补丁两组同时启用，先检查其额外开销；没有可靠指标时写明缺测，不填零或根据 FPS 推测。

现有慢回调数据带耗时阈值和来源数量上限，不能作为全部监听器或活动任务的清单；列表为空也不能证明退出后没有残留活动。

阶段耗时继续使用互斥口径。嵌套回调、goto 和帧阶段的包含时间不能相加。GPU 驻留、引擎池占用和进程工作集分别报告，不互相替代。

## 7. 实验协议与验收条件

### 7.1 对照设置

1. 锁定同一引擎提交和发布构建、同一渲染后端与开关。现有子树 A/B 保留为独立实验；本轮两组不改变子树开关。
2. 工具链验证额外保留“无逻辑修改回写版”，用于发现重建引入的行为和加载差异；正式 A/B 使用同一资源版本的原件与补丁。
3. 固定窗口、画质、播放倍率、地图、角色／素材顺序和等待条件。区分冷加载与预热循环，记录缓存条件及实际加载资源及其内容比对结果。
4. 初始协议建议每轮预热 5 次、测量 30 次打开／关闭或特效生命周期，至少做 3 对有效 A/B，交替运行次序。若操作较长可在 P0 调整，并在查看补丁结果前固定协议。
5. 另做每组 10～15 分钟固定轮次的长测，首尾返回同一场景。退出后按预先规定的异步完成条件取样，并单独记录正常完成 GC 后的资源盘点；不靠强制 GC 达标。
6. 每轮记录开始／结束标记、循环数、丢弃记录、错误、补丁命中、引擎版本与配置。未命中、不同场景、日志不完整或混入新引擎改动的轮次标无效并解释原因。

### 7.2 必须满足的正确性条件

- [ ] 正常关闭、自然结束、中途取消、快速复开、切换场景、对象池复用、重复清理和异步迟到场景均保持预期行为。
- [ ] 战斗完成、解锁输入等必需通知与基准一致且恰好一次，无丢失、重复或提前触发。
- [ ] 停用对象的自有活动归零，或回到 P0 记录的允许常驻集合；重复启用不使监听和回调数量倍增。
- [ ] 已销毁对象不会被过期回调重新挂载，复用后的新实例状态不被旧任务修改。
- [ ] 共享贴图仍可被其他使用者访问，淘汰后资源可重建，模型／面板复开无丢图、空白或新异常。
- [ ] 原版回退有效，未知资源版本不套用旧补丁，历史背包替换范围未被放宽。

### 7.3 性能与稳定性结论

- 对退出残留、空闲缓存和存活资源，比较相同操作点及完成 GC 后的序列；预热后应形成有界平台，不出现随循环持续增长的非预期项。允许常驻项及观察窗口需事先声明。
- 空闲缓存和池不超过已记录的数量／字节预算；活跃资源压力与空闲保留分别评价。
- 报告每循环分配／释放、退出后活动量、阶段耗时和原始逐帧中位数／p95／p99；没有逐帧数据时不报告逐帧分位。
- 性能门槛由 P0 基线波动及目标热点成本确定，至少跨有效重复轮次保持相同趋势。不能预设通用“提升 30%”或固定 FPS 作为验收线。
- 若主要目标是停止持续增长，资源收敛可作为修复收益，不能自动等同于已提升整体 FPS。进程 RSS 未立即回落也不能单独判为失败。
- 发现功能差异、共享资源提前释放、回调异常或目标指标恶化时，关闭对应补丁并保留证据；没有证据支持的提速写“未证实”。
