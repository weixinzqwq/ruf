奥拉Flux v1.0.0：messagesendservice.swf 公告屏蔽实现详解
分析日期：2026-11-22
性质：静态反汇编分析；没有执行 EXE、连接游戏或进行帧率/内存实测。

分析对象
- 上传文件：奥拉Flux v1.0.0.exe
- SHA-256：4a7cd5526e6099880bb11dca1f09cff0d71079e88d4e6fcab52a0da86f951639
- 内嵌主 PE 在原 EXE 的文件偏移：0x4595b
- 主 PE ImageBase：0x140000000
- 公告模块资源路径：overrides/aola.100bt.com/play/messagesend/messagesendservice.swf
- 该 SWF 为未压缩 FWS，长度 308856 字节，原 EXE 文件偏移 0x17fb9d8。
- 提取 SWF 与原 EXE 对应字节区间已核对相同。
- 本文 SWF 偏移均指方法字节码起始位置，不是原 ActionScript 源码行号。
- “伪代码”是依据指令重建的等价/简化表达，不是作者源码。
- 宿主 VA 与 SWF 文件偏移是不同地址空间，不可直接混用。

核心结论
aolaHideNotice 由本程序原生宿主实现。SWF 在多个时机调用这个接口，读取当前“屏蔽年费播报 / 全服公告”设置；真正提前返回、跳过对象创建、清空队列的动作发生在 SWF 的 ActionScript 逻辑中。
查到 6 个调用点、5 种通道名。所有通道读取同一个 hide_year_vip 布尔值，通道名只用于跟踪/诊断，并不是五个独立开关。
该机制减少一部分公告处理、对象分配、文本布局和动画调度。它不等于停止整个公告服务，不保证关闭正在显示的公告，也不是在网络层阻断服务器消息。

[N1] 宿主接口、设置映射与默认值

调用示例：
    ExternalInterface.call("aolaHideNotice", "random")

ExternalInterface.call 是 ActionScript 向 SWF 容器暴露函数发起调用并取得返回值的接口。在本样本中，容器是原生 Ruffle 宿主。

宿主等价伪代码：
    aolaHideNotice(args):
        category = args[0] 是字符串 ? args[0] : "default"
        对 category 做通道跟踪和诊断记录
        return Boolean(hide_year_vip 的全局镜像值)

UI 标签：
    屏蔽年费播报 / 全服公告

设置链：
    UI toggle("hide_year_vip", ...)
    -> 设置对象偏移 +0x25e
    -> 应用设置函数
    -> 全局字节 VA 0x142c00318
    -> aolaHideNotice 返回 Boolean

宿主证据：
- ExternalInterface 调度函数 VA 0x140377090。
- VA 0x14037750c 精确匹配 14 字节函数名 aolaHideNotice，转入 0x1403781db。
- 0x1403781db 起处理首个参数，非字符串或缺省时使用 "default"。
- 参数参与带锁的集合/诊断跟踪，未参与 random/honor/title/broadcast/coming 的独立策略选择。
- 所有返回路径汇合 0x140378cdc，读取全局 0x142c00318，返回 Boolean 类型。
- 应用设置函数 0x1402e2420：
  0x1402e2515 读取 settings+0x25e；
  0x1402e251c 写入全局 0x142c00318。
- UI 处理函数 0x1402554f0 匹配 hide_year_vip 后，
  0x140257924 写入 settings+0x25e，0x140258475 调用应用设置。
- hide_sincere_word 是另一设置，位于 settings+0x25d，全局为 0x142c0032d；
  aolaHideNotice 不读取它。
- 此宿主处理分支没有按战斗状态决定屏蔽结果的判断。

诊断文案：
    播报补丁已生效：通道 [<category>] 向宿主确认，当前开关 = <boolean>

默认值证据：
- 原生设置初始化函数 0x140f9aa80 中，设置对象基址为栈+0x138。
- 0x140f9aecb 清零栈+0x393..0x396，覆盖 hide_year_vip 字段所在的栈+0x396。
- 因此原生初始默认值为 false。
- 后续读取 aola-settings.json；解析器接受 hide_year_vip 或 hideYearVip，
  在 0x140f9f3d7 写入同一设置字段。
- 没有保存设置时默认不屏蔽；保存值可覆盖默认。
- 静态样本不能揭示用户当前运行时的实际设置。

[N3] 随机公告：初始化拦截与运行中拦截不同

方法 59 的伪代码：
    function initSystemdMsg():void {
        if (ExternalInterface.call("aolaHideNotice", "random") == true) {
            return;
        }

        msgArr = MessageMetadata.instance.getMsgArray();
        msgLen = msgArr.length;
        sTimer = new Timer(TIME_SLOT * 1000, 0);
        sTimer.addEventListener(TimerEvent.TIMER, onSystemMsgComes);
        sTimer.start();
        showTimer = new Timer(AUTO_CLOSE_TIME, 0);
    }

方法 68 静态初始化设置 TIME_SLOT=180，AUTO_CLOSE_TIME=5000。
因此，未屏蔽时，这里创建的随机触发定时器请求间隔为 180 秒；
showTimer 请求间隔为 5 秒。repeatCount=0 表示持续重复，显示结束流程会停止 showTimer。

如果这次初始化进入时开关就是 true：
- 不读取随机公告数组；
- 不创建这里的 sTimer；
- 不绑定和启动 sTimer；
- 不创建这里的 showTimer。
这个结论只覆盖 MessageRandomShow 这条初始化路径。

若此前已正常初始化、后来才开启屏蔽，方法 61 开头为：
    if (ExternalInterface.call("aolaHideNotice", "random") == true) {
        sTimer.start();
        return;
    }

这里确实是 start()，没有 stop()、reset() 或 dispose()。
因此已建立的随机触发定时器仍可继续存在；后续触发时，公告正文和显示对象创建被跳过。
这不等于销毁定时器，也不直接销毁当前已显示的随机公告。

未屏蔽时，方法 61 后续会停止 sTimer，获取随机文案，按需构造 SystemMsg、SystemTxt，
设置 htmlText、cacheAsBitmap、尺寸位置，加入显示容器，并绑定/启动 showTimer。
方法 64 onShowTimer 调用方法 63 removeMsgHandle；后者停止 showTimer、移除监听器，
stopAndRemove(sysTxt/sysMsg)、将两者置空，并重新启动 sTimer。
屏蔽分支没有直接调用这一套移除逻辑。

[N4] 事件入口：在消息生产前返回

三个事件入口首先判断同一布尔开关。

onHonorMsgDispatch：
- 入口屏蔽判断位于 event.params 业务处理之前。
- 被屏蔽时，后续参数解析、消息文案/链接拼接、MessageInfo 构造和入队不发生。
- honor 是处理器通道名，不能仅凭此词推断只影响某一种荣誉公告。

onTitleHandle 的等价伪代码：
    if (ExternalInterface.call("aolaHideNotice", "title") == true) {
        return;
    }

    var text:String = event.params.str;
    var info:MessageInfo = new MessageInfo();
    info.type = 16;
    info.name = "";
    info.content = 0;
    info.boxBody = text;
    messages.push(info);

onReturnBroadcast：
- 开关判断在读取 event.params.tn 和构造门槛数组之前。
- 正常路径使用人数门槛匹配；命中后创建 type=47 的 MessageInfo。
- 文案以“本期重逢有礼回归玩家已达”开头。
- 同一个 info 被 messages.push(info) 连续调用三次，即三条排队引用；
  不是创建三个不同的 MessageInfo。
- 屏蔽时，连这些门槛处理、消息构造和三次入队都省去。
- broadcast 对应这个回归广播处理器，不能由名称扩展为“所有网络广播都被过滤”。

这些处理器处理的是已到达本地业务层的事件。
aolaHideNotice 分支没有阻止 Socket 接收数据，也没有修改服务器奖励或活动状态。

[N5] 队列出口：丢弃待显示消息

方法 85 开头的等价伪代码：
    if (messages.length > 0 &&
        ExternalInterface.call("aolaHideNotice", "coming") == true) {
        messages.length = 0;
        return;
    }

关键顺序：
1. 先看队列是否非空。空队列时短路，不调用此处宿主接口。
2. 非空且屏蔽时，一次清空整个 messages 数组。
3. 清空后立即返回，后续消息取出和 messageImageGenerate 不执行。
4. 这段检查在 messageShowing、switchShow、任务完成状态和冷却状态检查之前。

未屏蔽时，正常路径还检查：
    !messageShowing
    messages.length > 0
    !switchShow
    finishNew()
    !interalDoing

随后设置 switchShow=true，messages.shift() 取出一条为 messageInfoNeed，
经过当前用户名相关检查后调用 messageImageGenerate()。

finishNew() 的名字容易误解：
方法 60 和 86 实际查询任务服务 isUserTaskFinish(150)，不是清理或结束公告的函数。

为何除了入口判断还需要队列判断：
- 开启屏蔽之前可能已有消息排队；
- 本模块还有 pushMessage 等其他入队路径；
- 在入口之后、显示之前开关状态也可能改变。
从结构上看，coming 检查用于覆盖仍留在同一待显示队列中的消息。
这是对执行顺序的分析，不能当作已经验证作者设计意图。

清空的含义：
- 已排队但尚未取出的公告被丢弃，不会在关闭屏蔽后自动补播。
- 清掉的是这个数组所持有的元素引用。
- 并非强制立即执行 GC，也不证明对象的其他引用已经消失。
- 不清空正在使用的 messageInfoNeed，不直接移除当前显示对象。
- 当 messageComing 因场景/战斗生命周期未被调用时，清理不会凭空即时发生；
  它是在下一次该消费者实际运行且检测到开关时执行。

[N6] “跳过图像创建”具体省去了什么

方法 88 messageImageGenerate，SWF 字节码偏移 0x4a740，
原 EXE 0x1846118，长度 1063 字节。

更准确的名称是“跳过公告显示对象、文本布局和相关定时器的创建”。
本方法没有发现直接 new BitmapData 的指令；不能把它描述成已经证明的位图像素缓冲分配优化。

方法正常执行会：
- 将 messageShowing 设为 true；
- 按消息类型选择 MessageBox5、MessageBox3、MessageBox4 等特殊公告容器，
  或创建 MessageBox1、TxtMessage、mcCloseView；
- 填写 TextField.htmlText；
- 用 gotoAndStop 选择相应背景/状态；
- 计算文字宽度、背景尺寸及 x/y 坐标；
- 绑定按钮点击、文本链接等事件监听；
- 将对象 addChild 到 LayerManager 的基础控制层；
- 常规滚动分支创建 moveTimer = new Timer(5)，绑定 onCountDown 并启动；
- 根据消息类型创建 2000、5000 或 10000 毫秒的结束定时器，绑定 ended 并启动。

这些 Timer 的数字是请求的延时。5ms 不等于已测得每秒精确执行 200 次。
AS3 Timer 文档说明实际事件时间受到帧率和运行环境影响；本样本的实际 Ruffle 调度频率没有实测。

从字节码执行顺序可推导的收益：
- 避免被跳过的消息对象/显示对象构造；
- 避免对应富文本解析、文本测量、位置计算；
- 避免将这些公告对象加入显示列表；
- 避免对应每条公告的移动与结束定时器、事件监听；
- 减少这些对象本会触发的后续渲染与回收工作。
不能仅凭这些事实量化 FPS 增幅、内存下降或 GPU 提升。

[N7] 当前已显示的公告与仍存活的服务

队列屏蔽分支没有做以下事情：
- messageInfoNeed = null；
- messageShowing = false；
- stopAndRemove(messageBox/txtMessage/mcClose)；
- 停止已有 moveTimer 或结束 timer；
- 注销 messageComing 的帧事件监听。

方法 91 onCountDown 自身不调用 aolaHideNotice，仍可更新公告位置。
方法 92 ended 正常停止 moveTimer、移除对应监听，调用 onClick(null)，
复位 switchShow，重置/启动 interalTimer 并设置 interalDoing=true。
方法 101 onClick 才会移除显示对象，并清空 messageBox、mcClose、txtMessage、messageInfoNeed。

因此，对于在屏蔽前已创建并正在显示的公告，屏蔽分支本身不会立刻让它消失。
它可继续沿原来的结束/点击关闭路径退出。其他模块可能有额外操作，但本次没有证据证明有主动强制清屏。

整个 MessageSendService 也没有被关闭：
- 方法 107 构造器仍创建 messages、MessageReader、curPosition 和 10 秒 interalTimer。
- 方法 70 init 仍绑定 socket、公示/称号、场景、战斗和冷却事件。
- 场景加载/卸载、战斗开始/结束会影响 messageComing 的 ENTER_FRAME 注册；
  屏蔽分支没有替代这套生命周期。

示例：
    当前屏幕上为 A；待显示数组中有 B、C、D。
    用户开启屏蔽后，下一次 messageComing 检查到 true：
        B、C、D 从队列丢弃；
        A 没有因此被主动移除；
        后续走受保护入口的新公告 E 会在构造前返回。
    用户关闭屏蔽：
        未来的新公告可重新走正常流程，但仍受显示互斥、任务门槛和冷却约束；
        B、C、D 不会自动补播。

随机公告恢复的限制：
若首次 initSystemdMsg 因屏蔽而提前返回，其定时器从未创建。
把宿主布尔值改回 false 本身不会自动造出一个不存在的 Timer。
在该 SWF 中没有看到“关闭屏蔽 -> 自动重新调用 initSystemdMsg”的路径。
若另有模块重新初始化服务，随机公告可能恢复；仅凭当前证据不能承诺恢复方式，
也不能直接断言这是已复现的产品缺陷。

[N8] 优化范围与不可推出的结论

能够确认：
- 自定义宿主布尔接口和游戏 SWF 逻辑相互配合。
- 存在初始化、消息生产入口、显示队列出口等多个拦截位置。
- 屏蔽可以避免相应公告的部分 CPU、分配和显示工作。
- 所有五类参数共用 hide_year_vip，默认 false，可由保存配置覆盖。
- 该逻辑属于对这条公告业务路径的定制减负。

不能由本证据直接推出：
- 停止所有 Timer；
- 停止整个消息服务；
- 所有弹窗、聊天、剧情、奖励提示都被屏蔽；
- 当前已显示公告马上销毁；
- 清队列等于立刻释放所有相关内存；
- 服务器不再向客户端发送公告；
- 修改了战斗数值、活动奖励或全服状态；
- 将 Ruffle 渲染器整体替换为更快算法；
- 任意确定幅度的 FPS/内存/功耗改善。
