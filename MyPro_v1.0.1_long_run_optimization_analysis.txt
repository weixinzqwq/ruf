MyPro v1.0.1：针对奥拉星长时间运行掉帧的优化差异分析
====================================================

分析对象：用户提供的 MyPro v1.0.1.exe，与 MyPro v1.0.0.exe 逐项对照。
关联材料：此前的 NewPetPackage_switch_stutter_analysis.txt 与原始背包 SWF。
方法：PE 结构检查、内嵌 SWF 提取/校验/逐字节比较、x64 反汇编、调用点和参数数据流核对。
本次未运行客户端，没有录制 30 分钟帧时间曲线；以下明确区分“代码已经改变”与“预期性能效果”。

结论
----

1.0.1 确实增加了针对长时间运行的原生层优化。最实质的变化集中在三个方面：

（1）减少长期闲置资源和历史缓存的保留：纹理池每规格保留数从 4 降到 1，增加老化和空桶删除；
     音频加入随 SWF 库、Sound 对象释放的生命周期管理，小音频不再总是引用整份大 SWF 数据。
（2）把清理接到更合适的时机：战后主清理之外增加约 2.2 秒后的补清理；首次主场景进入后
     安排两次维护；完整 GC 之后接入音频后端维护，并使用更积极的事件专用资源闲置阈值。
（3）减少 GPU 中间提交和等待：离屏/滤镜路径 flush 阈值从 64 提高到 1024，默认等待关闭；
     staging 分配块增大，并加入有待提交工作才执行相关 flush 的判断。

这些改动有真实的调用和释放路径，不能概括为只改了日志或只压低任务管理器的内存数字。
不过，静态分析不能证明用户的“玩半小时后掉帧”已经解决，也不能证明该现象只有一个原因。

另一项重要结果：两版可完整提取的 14 个内嵌 SWF 全部逐字节相同。1.0.1 没有通过这组
内嵌文件新增 NewPetPackage 的 AS3 修复。此前背包重复解析、隐藏页面响应刷新等问题，
不能仅凭这次原生层升级就认为已经消失。

二、纹理池：控制历史资源的积累
============================

2.1 每种规格保留的闲置纹理：4 → 1【已确认；E01】

旧版主帧结束时，对两组纹理池都传入保留数 4；新版相应位置改为 1。
消费参数的函数会检查每个 key 对应的闲置 Vec，缩短到指定上限，并逐项 drop 多出的
Texture/TextureView 引用。

这里的 key 表示纹理规格，例如尺寸、格式等组合。4 和 1 是“每规格闲置对象数”，
不是总纹理数、游戏帧数或 GPU 在途帧数。正在使用的纹理并不会因为这个上限被强制删除。
共享 offscreen buffer pool 的对应保留数量仍为 2。

对长时间运行的意义：持续接触不同界面、特效和模型，会产生许多规格的临时纹理。
把每一类留下的闲置资源减少，有助于降低累计保留量；快速重复访问同类资源时，则可能
增加重新分配或上传次数。它是复用率与驻留量之间的取舍。

2.2 第二组纹理池增加明确的 16 MiB 闲置预算【已确认；E02】

新版第二组池的维护调用传入 0x1000000，即 16 MiB。被调函数实际估算闲置纹理字节量，
超限后选择并释放候选，直到估算占用回到预算内。这组池的调用用途与离屏路径相关；
由于完整字段名未保留，本文以“第二组纹理池”指代，避免把字段名恢复程度说得过满。

边界：
  - 16 MiB 只约束该池可回收的闲置项，不是全部显存或整个程序内存的上限。
  - AOQI_IDLE_POOL_MB 仍然存在，两版默认都为 24 MiB；不能说全局默认从 24 改成了 16。
  - CPU 侧解除引用后，未完成 GPU 命令或驱动仍可能暂时保留底层对象。

2.3 新增老化，进一步删除长期空置的规格桶【已确认；E03】

新版在池中保存维护轮次 epoch，并在取得纹理时更新该规格的 last_used。
随后有两级清理：

  age > 30 个维护轮次：清空该规格的闲置纹理列表并释放引用。
  age > 240 个维护轮次，且闲置列表为空：将该规格 key 从哈希表移除，释放关联 Arc 和
  创建纹理的工厂闭包。

这项变化比单纯减少纹理数量更完整。即使一个规格的闲置纹理都已释放，它的 key、容器和
创建器仍可能留下；若历史规格持续增长，维护时扫描的对象也会变多。新版把长期空桶也删掉，
同时控制资源保留与历史表项的维护成本。

30 和 240 的单位是维护轮次，不是秒。常规主帧结束会维护，但其他入口也可能触发维护，
不能把它们直接换算成固定现实时间。

2.4 取得纹理时更频繁地检查预算：128 次 → 16 次【已确认；E04】

旧取得路径的低位判断为 test al,0x7f；新版为 test al,0x0f，并有真实的预算回收调用。
因此检查间隔从每 128 次取得调用缩短到每 16 次。单位是纹理取得次数，不是帧数。

推断效果：在一小段时间内密集建立临时纹理时，可以更早发现闲置池超预算；相应也增加了
检查频率，不能仅凭这个数值声称 CPU 总耗时必然下降。


三、音频：建立真正的注册声音生命周期
==================================

3.1 SWF 库与 Sound 对象接入生命周期 token【已确认；E05】

新版音频后端新增取得跟踪 token 的接口，调用实际接入了：
  - SWF 内嵌声音注册：注册声音取得 SoundHandle 后，获取 token 并存入所属 movie library。
  - AS3 SoundObject：保存 SoundHandle，并把对应 Arc token 存入对象；替换时释放旧 token。
  - AVM1 Sound：也有对应 token 持有和替换路径。

因此它不是只定义了一个没有调用者的新接口。对奥拉星 AS3 场景，前两条尤其直接。
该设计让“声音注册定义应当活多久”与真正的持有者联系起来。离开场景或战斗之后，
如果 SWF 库和 Sound 对象都已释放，后端就能够发现相应声音已失去这些持有者。

3.2 回收先检查持有者和活动播放，不会直接清空所有声音【已确认；E06】

实际维护流程可概括为：
  1. 获取正在播放的 SoundHandle 快照。
  2. 取出待处理登记队列，并校验句柄 index/generation，避免误处理已复用的槽位。
  3. 若 token 仍有有效强引用，则保留。
  4. 若声音仍在活动播放集合中，则延期处理。
  5. 否则移除声音登记与 mixer 中的声音定义，更新槽位状态并释放音频数据引用。

新版完整核心 GC 结束后会调用这个音频维护入口；声音注册入口也会先做维护。
旧版对应 GC 位置没有这次调用，相关维护虚表项原先还有直接返回的空实现。

必须区分两个概念：“停止一个声音实例播放”与“释放声音定义/压缩数据”不是一回事。
新版清理已经到达后者的数据结构，不只是把活动播放列表清空。

与长期运行的关系是工程推断：如果旧的注册声音及其数据在场景退出后继续保留，
多次战斗和加载 SWF 会让累计保留量增长；新增生命周期与后端回收为这类保留提供了出口。
本次没有实际统计某次会话累积了多少声音，也不能断言所有音频路径均已无保留问题。

3.3 小音频不再总是占住一整份大 SWF 缓冲【已确认；E07】

旧版已经有共享 SWF 片段的机制：声音可以保存原始 SWF 字节缓冲中的一个切片。
切片很小，但只要它持有底层共享缓冲的引用，整个缓冲就可能继续存活。

新版在片段有效性检查后增加了比例判断：

  原始 backing 缓冲长度 > 2 × 输入音频片段长度
      → 分配独立缓冲，只复制所需音频字节。
  否则
      → 继续共享原始缓冲中的片段。

这是一项很有针对性的长期内存保留优化。举一个纯说明性的例子：假设一个 20 MiB 的
SWF 只有 100 KiB 音频需要继续存活，共享切片可能仍保留全部 20 MiB 数据；复制音频
后，声音只需持有自己的小缓冲，原大缓冲在其他引用释放后就有机会回收。
这个例子不是从上传样本测得的节省量。

代价是注册声音时多一次分配和复制。MP3 分支会处理前两字节 seek 信息，实际复制长度
相应调整；两倍阈值比较使用的是调整前的输入片段长度，不是解码后 PCM 大小。
其他持有者仍可继续保留原 SWF，不能说一次复制就一定马上释放整份 SWF。

3.4 音频相关弱缓存会清除失效条目【已确认，但缓存 key 语义未完全恢复】

音频维护后半段在相关表的条目数大于 64 时，扫描并删除已无强持有者的 Weak 条目，
也会释放弱引用本身。这里是扫描触发阈值，不是最多同时播放 64 个声音、64 MiB 预算，
也不是严格把缓存容量限制为 64。报告不由此推定全部缓存键或宣称新增了全量音频去重。


四、战后与进入主场景时的清理调度
==============================

4.1 战后主清理之后，再安排约 2.2 秒的后续阶段【已确认；E08】

新版在战后主清理调用后，保存 now + 2 秒 + 200,000,000 纳秒的 deadline。
后续主循环在到期、当前不在战斗且 player 可访问时，进入 BATTLE_FOLLOWUP_MEM 路径。

这不是阻塞 2.2 秒，也不是每 2.2 秒固定执行。具体运行状态会影响它是否及何时被消费。
新增后续函数实际调用缓存维护、GC 选择和图形资源/渲染池清理，最后输出统计。

GC 选择有一个明确分支：
  登记的 SWF/library 项目数 > 305：调用完整核心 GC。
  否则：请求后续渐进收集，并执行资源维护。

305 来源于两个 library 登记表的长度之和，不是 305 MiB、亚比数量或显存数值。
渐进请求中的常量也不足以证明某个固定毫秒预算，本文不作这种推断。

合理的工程解释：战斗退出、显示对象撤下、库和音频引用断开、缓存闲置，可能不在同一
瞬间全部完成。补一轮维护能再处理主清理时仍被持有、稍后才变得可回收的资源。
这是用途解释；本次没有测到具体对象在第几毫秒释放。

旧版已有战斗范围/GC 和内存治理，所以准确说法是“新增专门的战后后续阶段及策略”，
不是“旧版从来不做战后回收”。

4.2 首次主场景就绪后，约 3.2 秒、12.2 秒安排两次维护【已确认；E09】

新版有 ROOM_ENTRY_MEM 与 ROOM_ENTRY_FOLLOWUP_MEM 两个阶段。
二者都通向完整核心 GC 加统一资源维护的入口。

这一机制受一次性状态位限制：当前 player 首次满足房间/主场景状态后设为已安排，
在 player setup/reset 时才重新清零。因此它通常针对一次 player 会话进入主场景的过程，
不是每次切地图都执行两轮，也不是持续每 3.2 秒或 12.2 秒全量 GC。
其他状态分支还可能清掉 deadline，时间值是调度目标而非实际准时执行保证。

对“玩半小时后才变慢”的覆盖：这两轮更直接针对入口、登录和主场景建立阶段的残留。
如果后续长时间留在同一地图，它们本身不会自动成为半小时后重复执行的周期清理。

4.3 事件专用的闲置资源门槛更积极【已确认；E10】

统一维护包含：character 图形资源登记、tessellation 几何细分缓存、其他缓存、纹理池和
渲染缓冲维护。反汇编已经看到清空资源句柄以及 Arc 引用递减/drop，并非只记录统计。

专用入口参数：
  战后主清理、战后后续：图形资源闲置门槛 0.2 秒；细分缓存使用 0.2/0.5 秒两档条件。
  主场景入口、入口后续：图形资源闲置门槛 0.4 秒；细分缓存使用 0.4/1.0 秒两档条件。

细分缓存还有规模条件，不能把时间门槛理解成唯一条件。character.rs 的 character 是
SWF 字符/图形资源定义，不能译成“只清理游戏亚比”。

0.2/0.4 秒表示资源多久没使用就成为清理候选，不是这次清理最多占用 200/400 毫秒。
旧版另一个 quiet 入口使用 6 秒门槛；由于触发入口不同，不能说全部全局默认统一
从 6 秒或 8 秒改成 0.2 秒。

这能更早释放近期退出内容的缓存，代价是很快再用到时重新构造、细分或上传。
完整 GC 与集中回收本身也可能造成瞬时耗时，因此“驻留更低”与“帧时间更平稳”需要
分别测量。


五、GPU 提交：减少中间同步，调整上传和回收配合
==========================================

5.1 AOQI_FLUSH_EVERY 默认 64 → 1024【已确认；E11】
5.2 AOQI_FLUSH_WAIT 默认 true → false【已确认；E11】

这些选项名字在旧版就存在，改的是默认值。环境显式设置仍可覆盖默认行为。
实际 maybe_flush 位于离屏绘制和滤镜相关调用路径，计数超过阈值时会提交中间命令、
处理 staging，并按等待标志决定是否等待对应 GPU submission。

关键单位：64/1024 是 maybe_flush 的调用计数阈值，不是游戏帧数；函数用严格大于比较，
从零开始且没有其他重置时，相应会在第 65/1025 次触发。正常主画面仍按帧提交。

预期效果：减少一帧内部若干离屏/滤镜工作的提交次数，默认不在这条中间 flush 路径
同步等待 GPU，减少 CPU 与 GPU 之间的串行停顿。

边界：在途帧限制、显式读回和其他路径仍可能等待；较大批次也可能暂时保留更多未完成
工作。不能把它写成“完全取消 GPU 同步”，或把 1024 理解成显存预算。

5.3 StagingBelt 分配块 64 KiB → 256 KiB【高置信度；E12】

构造参数从 0x10000 改成 0x40000，后续 finish/recall 调用结构与 wgpu StagingBelt 相符。
该参数是临时上传缓冲的分配块大小，不是总上传字节预算。

较大块可降低大量小上传中频繁建立小块的管理成本，但也增大单块占用。wgpu 官方文档
用于解释该 API 的分块与复用语义；本项目具体变化仍以两版机器码为准，不能用官方
文档版本直接推定 MyPro 所用的精确依赖版本。

5.4 新增 pending-work 标记，相关回收/读回入口按需 flush【已确认；E12】

新版在 ActiveFrame 维护独立的待提交工作标志，写入工作时置位，主帧提交后清零。
新 helper 在没有待提交工作时直接返回，有工作才结束 staging、替换 encoder、提交并
recall。该 helper 已接入缓冲回收及另一读回样路径。

这使这些入口只在存在待提交工作时执行提交步骤。由于一个调用点的完整高级函数名没有恢复，
本文不将其硬对应为某一个 Flash API，也不宣称所有空提交都已经消除。

5.5 GPU 在途帧限制原来已有；新的是环境覆盖与零限制时的 poll【已确认；E13】

两版都存在 --gpu-frames-in-flight，CLI 默认都为 2；两版都维护提交队列，并在超过
非零限制时等待较早提交完成。因此“新增默认最多 2 帧”不属于本次升级的差异。

1.0.1 新增 AOQI_MAX_IN_FLIGHT：成功解析后覆盖宿主配置，否则回退宿主设置。
新版在 limit=0 时仍执行非阻塞 Device::poll；旧 wrapper 的零限制分支直接退出。
这能推进设备事件/回收处理，但不是一次强制阻塞等待全部 GPU 工作完成。

两版等待路径都有 2 秒 timeout 参数。它表示等待上限，不能因用户恰好卡 2—3 秒，
就认定卡顿来自这个值；需要运行时调用栈和帧时间证据。


六、哪些属于继承旧版，哪些没有证据表明已修复
==========================================

6.1 14 个内嵌 SWF 全部相同【已确认；E14】

网络动态下载文件、外部覆盖包和实际启动配置不在本次内嵌文件同一性结论的范围内。

6.3 弱引用与 SWF URL 分类主要沿用旧版

AOQI_WEAK_UNIT_MOVIE 读取器旧新规范化的 57 条指令一致；默认模式为 2，精确值
"1" 选择模式 1，"oneoff" 选择模式 2，其他已读取的值返回 0。
URL 分类表从 41 项变成 40 项，唯一集合差异是移除 /play/weblogin/，没有增加路径。
对普通 weblogin 资源，它不会再仅凭这条路径命中原来的一次性弱 movie 分类。

这更像登录模块保留/稳定性分类的修正，不是新增一整套弱引用回收体系。其他模式与
匹配条件仍会影响具体结果。AOQI_WEAK_VALUES、AOQI_WEAK_DYNAMIC、AOQI_RECLAIM_ATOMIC
相应读取逻辑也与旧版相同。

  - 战斗范围/GC 开关 AOQI_BATTLE_GC 和已有内存治理。
  - GPU 在途帧控制及默认 2。
  - AOQI_IDLE_POOL_MB 及默认 24 MiB。
  - QueryVideoMemoryInfo 查询。
  - 先前已有的资源缓存、部分 AS3 热点 native 化、bounded blend/glow 等。

本次没有确认新增了“所有不可见/脱离显示树的 MovieClip 自动休眠”机制。
GC 统计中的 dormant 字样不足以证明时间轴、ENTER_FRAME 或定时器已经停止执行。
也没有发现足以支持“每过半小时统一清理一次”的新增定时策略。

6.5 内嵌更新说明的其他内容

宿主 HTML 更新说明提到图形后端快捷选择、工具栏布局，以及亚比骨骼、部分文字、

七、为什么这些改动仍不保证解决半小时后的卡顿
==========================================

7.1 几类现象的针对性不同

现象                                  与本次改动的关系
切图/战斗越多，占用越高                纹理空桶清理、音频生命周期、战后补清理有直接针对性。
同地图挂机也越来越慢                   要区分活跃脚本、事件/时间轴、资源继续生成及宿主任务。
内存下降，但仍频繁单帧长停顿            需检查同步 GC、缓存重建、tessellation、上传或 GPU 等待。
仅点击切换亚比时固定停顿                原背包重复解析/广播刷新仍是需要单独处理的候选。
帧率变低而内存并不持续增长              不能仅凭内存治理解释，应检查实际 CPU/GPU 时间分布。

表中是诊断方向，不是对用户设备已经测得的结论。

7.2 GC 处理不了仍然需要保留的强引用

若面板、监听器、定时器、静态容器或其他对象仍持有资源，GC 必须把这些活对象保留下来。
清理纹理池也不会自动减少这些 AS3 回调的执行次数。隐藏页面即使不可见，只要仍在响应
事件或执行时间轴，CPU 成本仍可存在。这里是一般生命周期约束，并非本次已经证明
用户会话恰好由某个监听器泄漏导致。

7.3 更积极回收可能把累计成本变成重新进入时的瞬时成本

纹理、几何缓存、声音和缓冲更早释放后，再次使用可能重新分配、细分、复制或上传。
完整 GC 同样可能占用主循环时间。因此评价目标要同时包含长期占用趋势和帧时间尾部。
仅比较平均 FPS 或任务管理器的某一次内存数字，会漏掉卡顿本身。

7.4 工作集下降不等于对象/显存保留已经消除

已有的 EmptyWorkingSet 等操作可以改变物理页驻留；共享引用、分配器保留和 GPU 未完成
命令又会影响何时真正归还资源。判断改动有效，需同时看私有提交、资源条目和帧时间。
本版存在真实对象释放路径，仍不意味着每次调用马上出现同等幅度的 OS 占用下降。


八、后续验证与继续优化的优先级
============================

8.1 用同一场景路线比较 1.0.0 与 1.0.1

固定图形后端、窗口尺寸/分辨率、音频设置、帧率限制、外部覆盖和环境变量，分别记录
启动稳定后、10 分钟、30 分钟、60 分钟的数据。至少分三种路线：
  A. 同地图挂机：减少内容切换，观察无切换时的积累。
  B. 固定切图和战斗循环：观察 SWF/声音/纹理历史资源是否逐步回落。
  C. 固定亚比背包切换循环：观察背包同步刷新与模型初始化的瞬时耗时。

应记录：
  - 帧时间分布，尤其 p95/p99 和长帧数量；平均 FPS 只作辅助。
  - 进程 Private Bytes/私有提交和 Working Set，并区分二者。
  - GPU 专用/共享占用及预算状态；若环境能提供，同时记录等待时间。
  - SWF/library 条目、已注册声音、活动播放、纹理规格桶、闲置纹理字节等计数。
  - 完整 GC、渐进请求、资源 trim 的时间点及耗时。

可关联已有的新日志标签 BATTLE_FOLLOWUP_MEM、ROOM_ENTRY_MEM、
ROOM_ENTRY_FOLLOWUP_MEM。标签出现只证明到达对应统计路径，是否改善帧时间仍需对照。
若发行版日志不暴露上述细项，需在可修改的源码中加观测；本文未声称已获得全部运行计数。

8.2 如果继续做 Ruffle/奥拉星定制优化，优先级建议

第一优先级：保留本版可验证的生命周期闭环。
  音频定义跟随 SWF 库和 Sound 的拥有者释放；活动播放延期保护；小片段避免保留大缓冲；
  纹理池不仅删闲置对象，也删长期空规格桶。应以资源计数能回落来验证。

第二优先级：给重清理和重新加载分别计时。
  将战后 full GC、后续渐进请求、细分缓存释放、缓冲重建分别量化，避免依靠增加 full GC
  频率解决所有问题。选择合适的触发点与工作量需要实际帧时间支持。

第三优先级：独立修复背包同步 AS3 路径。
  针对此前报告的详情重复解析、不可见页面刷新和重复槽位更新做缓存或更新范围控制；
  再测模型装入/细分/上传成本。1.0.1 现有内嵌 SWF 差异不能替代这一步。

第四优先级：按图形后端实测提交策略。
  flush 阈值、等待、staging 块和在途帧配置会同时影响延迟、吞吐与峰值占用。
  不应在没有同场景 A/B 数据时把某个参数宣称为所有设备最优，或直接无限增大批次。

本次最有证据的判断是：1.0.1 已对原生资源的保留、退出后的回收和 GPU 同步成本做了
多项具体修改；对于仍存在的长期掉帧，需要进一步辨别剩余增长来自活跃 AS3、音频/库、
图形缓存还是 GPU 等待，再对相应路径继续修改。
