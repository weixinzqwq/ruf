# AVM2 数组存储的自主重建

此处是以官方 Ruffle 源码为基础的新实现，不是从 EXE 找回的原始 Rust 文件。发布版证明存在分离 payload/tag 的紧凑存储；原 GC 指针及枚举的完整 ABI 未恢复，因此这次不直接使用原始 discriminant 数字编码 Rust 对象指针。

## 接入位置

`core/src/avm2/array.rs` 中真实的 `ArrayStorage::Dense` 已改用 `dense_storage::DenseStorage`。构造、AMF 替换、读取、写入、删除、长度调整、枚举、push/pop、shift/unshift、splice、稀疏转换都经过该容器，未增加未调用的演示库。

`dense_storage.rs` 对长度达到16的纯原语数组使用分开的 `Vec<u64>` payload 与 `Vec<u8>` tag；构造时预留容量达到16也直接采用这个表示。它保留 hole/undefined/null/bool/i32/f64 的区别、NaN payload 和负零。元素有效载荷为9字节；容器头、Vec容量及分配器另计，不能据此声称整个进程节省43.75%内存。16为重建时的保守阈值，不是原始配置声明。

遇到字符串或对象时先提升为上游的 `Vec<Option<Value>>`。引用仍是带 `'gc` 生命周期的原始类型，继续由 `gc_arena::Collect` 跟踪；没有把指针改成整数、没有 `unsafe`、没有绕过调用者原有的 ArrayObject 写屏障。完整泛型/对象紧凑表示未恢复，这个安全回退也意味着对象数组不会得到本次原语压缩收益。

## 小数组成本与收益边界

**这个实现存在额外头部成本，不能保证所有数组或整个程序的内存下降。** 在Windows x64上，原 `Vec<Option<Value>>` 头部由三个机器字组成，计24字节。新 `DenseStorage` 的最大变体包含两个Vec，仅变体字段就需48字节；枚举判别与对齐还可能增加空间。即使当前使用 `Full` 变体、甚至是空数组，这个内嵌枚举也必须容纳最大变体。因此仅这个字段就有至少24字节的新增空间需求；完整 `ArrayStorage` 还有外层枚举布局，其最终增量受编译器的niche/对齐布局影响。本次没有输出整个 `DenseStorage` / `ArrayStorage` / `ArrayObject` 的实际 `size_of`，上述是字段布局下界，不是完整类型的测量结果。

- 从空数组逐步增长且仍小于16项时，仍用Full的原元素表示，同时承担较大的枚举头；这些小数组会有成本。
- 包含字符串或对象而保持Full的数组没有元素压缩收益，也承担较大的头部。大量小数组或对象数组可能让总内存反而上升。
- Primitive通常有两次堆分配而不是一次，还需计入分配器元数据、分配粒度和两个Vec各自的剩余容量。
- 从Primitive提升到Full时，需要先分配并填充新的Vec，然后释放原有两个Vec，会短暂同时占用两种表示；提升也有逐元素复制成本。

设旧元素区容量为 `C_old`，新payload/tag容量为 `C_payload` / `C_tag`，`V = size_of::<Option<Value>>()`，完整容器头部增加量为 `ΔH`，分配器相关额外成本为 `ΔA`，则净节省需要满足：

```text
V × C_old > 8 × C_payload + C_tag + ΔH + ΔA
```

仅在三种容量相同且 `V=16` 的假设下，才简化为 `7 × C > ΔH + ΔA`。例如假定头部增量32字节、忽略分配器成本，则5项才在算术上抵消头部成本；16项时元素区少112字节，再扣32字节后剩80字节。这只是说明平衡点的条件计算，32字节不是本次完整类型的实测值，16项也不能保证真实分配器下的净收益。阈值与表示策略仍需真实游戏的数组尺寸/类型分布和内存测量来校准。

## 验证

在引擎目录运行 `cargo test -p ruffle_core --lib avm2:: --offline`：

- 原有 ArrayStorage 占用数测试保持，包括 holes、删除、长度调整、splice、pop/shift等。
- 原语位模式用例区分hole与undefined，覆盖i32极值、正负无穷、负零、NaN与非正规数。
- 6,000步确定性混合操作与标准Vec模型逐项对照，包括长度调整、插入、删除、splice和pop。
- 1,024个整数数组按实际Vec容量检查两个元素区的字节数小于原Option<Value>元素区；这个测试没有包含容器头、分配器元数据或整个进程内存。
- 在真实gc-arena中创建字符串后提升、完整回收多轮并读回，验证引用保留。

测试结果以交付的构建日志为准；这些不等于游戏运行、FPS或整体内存曲线测试。

## 保留的边界

`ScriptObjectData.slots`、trait map、动态属性及对象引用布局继续使用上游实现。本次没有把更大的容器头无条件放进每个ScriptObject，以免大量小对象反而增加内存占用。后续要压缩这些结构，需要结合完整GC tracing和真实工作负载重新验证。
